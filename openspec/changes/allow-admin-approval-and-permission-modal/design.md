# Design

## Context

Approval authority is checked both by the `ApprovalsController` role filter and by `ApprovalService`. The controller currently applies one role filter to approve and reject actions. The static UI handles decision failures in a page-level alert, and the permission-denied text is generated by `RequireRoleAttribute`.

## Goals / Non-Goals

**Goals:**
- Keep the Admin role explicit at the API boundary while applying Director approval rules in the Domain.
- Present role authorization failures through an accessible, dismissible modal whose state is cleared on session changes.

**Non-Goals:**
- Change Manager or Director limits, self-approval prevention, or high-value approval rules.
- Grant Admin permission to reject invoices or change the server's permission-denied message.

## Decisions

- **Apply Director-equivalent limits to Admin in the Domain.** Keep `ApproverRole.Admin` explicit and permit it through the same amount and distinct-approver paths as Director. This avoids translating an Admin identity into a different role at the controller boundary and retains the existing no-HTTP/no-role-string Domain separation. Do not bypass amount or two-person checks.
- **Scope API authorization to individual actions.** Apply Manager/Director/Admin authorization to approval only and retain the current Manager/Director authorization for rejection. Keeping the controller-level authorization broad enough for both actions would unintentionally grant Admin rejection.
- **Use an accessible native modal dialog for role-denied feedback.** Detect the existing permission-denied 403 in the UI decision flow and display that message in a dismissible dialog; keep other decision errors in the existing inline error path. Close and clear the dialog when the user dismisses it or the session changes, rather than storing its message in session state.
- **Test at each boundary.** Add Domain coverage for Admin's Director-limit and distinct-second-approver behavior, API coverage for Admin approval versus Admin rejection, and focused UI/browser coverage for modal opening, dismissal, and session cleanup.

## Risks / Trade-offs

- [Action-level filters can accidentally leave an action unprotected] → Add API tests proving both Admin approval succeeds when eligible and Admin rejection remains forbidden; retain role checks on both actions.
- [A dialog opened during an asynchronous decision could outlive the session] → Close and clear it from sign-out/session-reset handling, and do not persist permission feedback in storage.

## Migration Plan

No data migration or API contract change is required. Deploy the application update normally; rollback by reverting the application change.
